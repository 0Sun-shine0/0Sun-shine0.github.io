一条数据为什么会悄悄退回备份

待办没报错，却少了几条。查到是 UTF-8 BOM 让 json.load 抛了异常，程序又把它当成文件损坏、静默回退到备份 —— 数据看起来就「凭空少了」。

2026-09-218 分钟Python数据可靠性踩坑

这是我最不想再遇到的一类 bug：没有任何报错，数据却少了。

现象是这样的 —— 有人反馈「我今天加的那几条待办不见了」。打开程序一切正常，只是数据看起来退回到了两天前的状态。没有崩溃、没有弹窗、没有日志报警。

排查：为什么它看起来一切正常

程序里有一条自我保护逻辑：主数据文件读不出来时，从备份恢复，保证工作台能打开。

try:
    data = json.loads(path.read_text(encoding="utf-8"))
except Exception:
    data = load_backup()   # ← 就是这里

这条逻辑本身没错，它救过很多次场（断电、写一半被杀、同步盘回写冲突）。但它把两种完全不同的事情归成了一类：

  1. 文件真的坏了 —— 备份是唯一能救的。
  2. 文件其实完好，只是我读它的方式不对 —— 这时候应该报错给我，而不是悄悄换一份旧数据。

在这个 case 里是第 2 种。

根因：文件开头多了三个字节

json.load 抛的异常是：

JSONDecodeError: Unexpected UTF-8 BOM

原因很具体：Windows 记事本、以及不少编辑器的「另存为 UTF-8」，会在文件开头写一个 BOM（EF BB BF）。用 encoding="utf-8" 读的时候，这三个字节变成了字符串开头的一个 \ufeff，JSON 解析器看到第一个字符就不是 { 或 [，直接判定非法。

于是链路是这样断的：

用户用记事本改了一下 pet_data.json（也许只是想看看）
        
文件开头多了 EF BB BF
        
json.load 抛 JSONDecodeError
        
except 捕获 → 判定「主文件损坏」
        
静默加载备份 → 用户看到的是旧数据
        
没有任何提示

用户的真实感受是「我加的东西丢了」，而且根本不知道发生了什么。

修法其实只要一个词

path.read_text(encoding="utf-8-sig")

utf-8-sig 的行为是：有 BOM 就吃掉，没有 BOM 时与 utf-8 完全一致。 所以这是纯收益的改动，没有任何兼容风险。

顺带说一句：这个问题值得记住的原因是它到处都是。任何「用户可能用 Windows 上的编辑器碰过」的文本文件 → JSON、CSV、.env、脚本 —— 都可能遇到。如果你的程序读这类文件用 utf-8，它就在等着被 BOM 咬一口。

但只改编码还不够

修完之后我意识到：「读不出来」和「从头来过」之间被我用一个 except 直接连上了，这才是危险的地方。

所以那一版一起改了三件事。

一、逐项容错，而不是整体回退

原来一份文件里任何一处解析失败，整个文件都不要了。现在改成：能读出来的部分照常用，坏掉的那一项退回默认值，其余数据不受影响。

pet_data.json 里装着待办、便签、提醒、专注记录和设置 —— 没有任何理由因为「一条提醒的格式不对」就把所有待办一起丢掉。

二、坏文件改名保留，绝不覆盖

数据文件确实损坏时，旧版本会直接覆盖它写一份新的 —— 等于把唯一可能抢救的原始证据抹掉了。

现在的做法是把它改名保留：

pet_data.json            当前数据
pet_data.json.broken-20260921-1130    坏掉的原文件，留着
pet_data.json.bak        备份

万一需要人工抢救（打开看看哪一段坏了、手工修回来），原文件还在。这个改动成本几乎为零，但它把「数据丢了」从不可逆变成了可逆。

三、写盘用原子替换

# 写临时文件 → fsync → 原子替换 → 保留上一份为备份
tmp.write_text(json.dumps(data, ensure_ascii=False))
os.replace(tmp, path)

直接往目标文件上写是「写一半崩溃就丢数据」的经典写法。原子替换保证任何时刻磁盘上都有一个完整可用的文件。

最后补一条回归测试

这个 bug 最气人的地方是它从来没被测试覆盖过。所以补了一个很小的测试：手写一个带 BOM 的数据文件，然后断言它不会被判定成损坏。

def test_bom_file_is_not_treated_as_corrupt(tmp_path):
    # 前三个字节是 BOM，后面是完全合法的 JSON
    (tmp_path / "pet_data.json").write_bytes(b"\xef\xbb\xbf" + b'{"todos": []}')
    data = load_data(tmp_path)
    assert data is not None          # 不能回退到备份

现在 tools/bomproof.py 里保留了一份最小复现，回归测试也跟着走。

写在最后

这次排查最后留下的一句话是：不要用 except 把「读不出来」直接升级成「从头来过」。 先问自己两个问题：

  1. 有没有可能只是我读的方式不对？（编码、BOM、换行符、权限）
  2. 就算真的坏了，能不能做到「部分可用」？

这两个问题问完，多半会发现「静默回退」既不是唯一选择，也不是最好的那个。

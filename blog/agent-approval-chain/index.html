我给桌面操作加的两道硬限制

小爪能操作键鼠、读文件、跑命令，所以有两个动作即使在「完全自动」下也要再问一次。为什么这么分，以及这类判断该写在审批链的第几行。

2026-09-239 分钟Agent权限设计安全

小爪助手能看屏幕、点鼠标、敲键盘、跑命令和读文件。做这类功能时，我最先遇到的不是识别问题，而是一个更实际的问题：用户凭什么敢按下允许。

所以我做了一套权限分级，默认是逐步确认：

等级 行为
只读 只能看屏幕，任何会动键鼠的操作直接被拒
逐步确认（默认） 点击、输入、按键前都弹卡片问你
自动执行 只读和键鼠自动跑，执行命令仍需确认
完全自动 不再询问（谨慎用）

看起来「完全自动」就是「别烦我」的开关。但它有两个任何档位都免不掉的例外：

  • 装自定义工具（install_extension） —— 装的时候弹一次卡片；
  • 跑 code 档的自定义工具 —— 每一次运行都单独弹一次。

为什么这两件事始终要问

full（完全自动）的含义应该是「你信任这些已经配好的动作」，而不是「你信任接下来将要生成的代码」。这两件事差得很远。

小爪支持让 AI 生成自定义工具：重复的工作（整理工单、按固定格式汇总、从某个目录挑日志）可以先生成一个小工具，之后每次按同样的规则执行。工具有三档：

档位 做什么 要不要确认
固定说法 一段固定指令，不碰文件、不联网 不用
固定流程 一串只读步骤（读文件 / 列目录 / 正则提取） 不用
自定义代码 真跑 Python 每次运行都要确认

现在假设 full 能免掉这两个例外，会发生什么：

用户开着「完全自动」
   
模型写出一段 Python，装成工具（静默生效）
   
模型运行它（静默执行）

这等于给它开了一条路：自己写代码，然后自己悄悄跑掉。 用户在整个链条里没有做过任何决定，而这条链的终点是「任意代码在这台电脑上执行」。

给自动生成的代码开一条静默生效的路，本质是把「用户自己决定要不要跑这段代码」这件事从流程里删掉了。

这个判断应该放在审批链最前面

这类判断的实现，位置比逻辑更容易错：

def needs_approval(self, action, level) -> bool:
    if action.risk is Risk.CRITICAL:
        return True          # 装工具 / 跑自定义代码
                             # 写在后面等于没写
    if level is Level.FULL:
        return False
    return action.mutates    # 只读的不问你

Risk.CRITICAL 必须放在第一行。因为下面每一档都会给「完全自动」提前 return False —— 这条链以前正是从那儿钻过去的：先命中了 full 的豁免，等轮到危险等级判断时已经返回了。

这是那次自评审里发现的 P0。顺序敏感的判断，一律写在最前面。

卸载工具为什么不在例外里

卸载一个工具不在例外里 —— 它是普通确认，full 模式下不问。

理由很实际：它删的是你自己装的工具，而且有回收站兜底能捞回来（卸载时定义先进 extensions.removed.json，说一句「把刚才那个加回来」就能恢复，连「用过多少次」都还在）。

把每一件小事都升级成必弹卡片，结果只会是用户学会闭眼点「允许」。 那样真正的危险确认也会被一起点掉。

我最后保留的三道保险

保险 做法 它负责什么
急停 鼠标快速甩到屏幕左上角，立刻中断 出问题时的一秒逃生
危险命令黑名单 format、diskpart、shutdown、del /f /s /q C:\ 直接拒 防手滑
审计日志 每次动作记录「谁批准的、几点几分」 事后可查

黑名单要说清定位：它是防手滑，不是安全边界。 真正的边界是审批卡片和审计日志。挡的是「连问都不该问」的那一类 —— 格式化磁盘、删盘根、擦分区表 —— 这些操作没有任何正常用途，所以不给模型开口子的机会。但一个会写命令的模型总有办法绕，别把它当沙箱用。

黑名单本身也有讲究，两个点：

归一化。 匹配前先把写法压成「最坏情况的样子」：

  • 去掉 ^（cmd 的转义符，^f^o^r^m^a^t 真的能跑）
  • 去掉引号（del /f /s /q "C:\" 和 del /f /s /q C:\ 是同一件事）
  • 空白压成一个空格（vssadmin delete 两个空格原来就漏了）

看目标，不看开关。 判定的是「这个操作作用在什么上」，不是「命令里出现了哪些关键词」：

  • rd /s /q build → 放过（常规构建清理）
  • rd /s /q C:\Users → 拒绝

误拦比漏拦更糟 —— 它会训练用户把整个黑名单关掉。「必须拦」和「不该误伤」两张表我都写进了测试，一共 46 条。

没有明确同意，就按拒绝处理

批量操作（一次问好几个动作，见另一篇）里始终遵守 fail closed：

  • 高危操作绝不合并，永远单独问、用人话描述；
  • 只读操作不参与询问（本来就不问）；
  • 超时、没勾选、没表态 —— 一律按拒绝处理。

不确定的时候往安全那边倒，成本只是多做一次确认；往另一边倒，成本是不可逆的。

写在最后

做完这一套之后，我对「安全设计」的理解变了一点：

它的产出不是「更少的弹窗」，而是「用户真的会看的那些弹窗」。

所以判断标准不是「危险动作有没有全部拦住」，而是：用户有没有对「需要他想清楚的每一步」保持警觉。要做到这点，就必须允许某些小事不问 —— 否则确认疲劳会替攻击者把所有门都打开。

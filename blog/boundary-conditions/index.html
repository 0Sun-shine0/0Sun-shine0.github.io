从一道「字符串解码」看边界条件是怎么漏掉的

第一次认真刷算法题，思路三分钟就想出来，然后连挂四次。写得比较啰嗦，因为那时候我确实没想清楚，只想把过程记下来。

2024-03-168 分钟算法刷题边界条件

2024 年 3 月我开始刷算法题。

之前写代码都是「能跑就行」，没系统学过算法，也不太清楚刷题到底该怎么刷。第一篇笔记想认真写点什么，但当时水平有限，可能写着写着就乱了。

让我卡住的是「字符串解码」（LeetCode 394）。题目大意：给一个 3[a2[c]] 这样的字符串，要输出 accaccacc，括号可以嵌套。

思路我看题解学过：用栈。遇到数字记下来，遇到 [ 把当前状态压栈，遇到 ] 出栈拼回去。看着不复杂。

我照着写出来是：

def decodeString(s: str) -> str:
    stack, num, cur = [], 0, ""
    for ch in s:
        if ch.isdigit():
            num = num * 10 + int(ch)
        elif ch == '[':
            stack.append((cur, num))
            cur, num = "", 0
        elif ch == ']':
            prev, k = stack.pop()
            cur = prev + cur * k
        else:
            cur += ch
    return cur

跑题目给的示例 3[a]2[bc]，输出 aaabcbc，对。提交，挂了。

后面连着挂了四次。我按顺序记一下，尽量把当时在想什么写清楚。

第一次挂：12[a] 只输出了一个 a

报错用例是 12[a]，我输出的是 a。

第一反应是「两位数没处理」。但代码里写了 num = num * 10 + int(ch)，理论上应该没问题。

盯着看了挺久，最后是猜的：可能 num 清零的位置不对。我就把清零从 if ch.isdigit() 那一支挪到 [ 那一支，再提交，过了。

现在回头看，我当时其实没搞明白为什么这样改就对了。 只知道「这样改能过」。

第二次挂：嵌套的时候又不对

这次是 2[3[a]]。我输出的是 aa，应该是 aaaaaa。

我用了一个很笨的办法：往代码里插 print。

print("遇到 ] 了, cur =", cur, " prev =", prev, " k =", k)

打印出来才看到，内层出栈的时候 cur 是 aaa 没错，但外层拿到的 prev 是空的。

原因是我前面「修 12[a]」的时候，把 num 的清零挪了位置，顺手也影响了嵌套的结构。具体怎么影响的，说实话我到现在也不能一句话说清，反正挪回去、换个写法之后就好了。

第三次和第四次挂：代码里留了调试用的东西

这两个我合在一起写，因为原因差不多，都是我自己手欠。

调试的时候为了方便，我加了：

result = cur
return result

改回来的时候没改干净，留了个 return s，所以全部用例都输出原始字符串。

改掉之后又挂了一次，这次是 return stack[0]。我当时想当然地觉得「栈里应该存着最后的结果」。

复盘：四次挂掉的原因不太一样

第几次 现象 我当时以为的原因
1 12[a] 输出 a 两位数没处理
2 2[3[a]] 输出 aa 嵌套没处理
3 全部输出原字符串 （找不到原因）
4 全部输出空 栈用错了

这里面真正算「算法」问题的，我后来想想，可能只有第一次的一半。

第 3、4 次尤其气人，因为代码逻辑其实没坏，是我改调试代码没改干净。

一些当时的收获

写完这道题我做了几件事，现在看都挺笨的，但确实有用。

第一个是抄了一份边界用例清单。

我一开始完全想不出该测什么，是看了讨论区才知道还有 12[a] 这种两位数、还有嵌套的写法。所以我把能想到的情况都列出来，贴在代码旁边：

  • 空字符串
  • 只有字母没有数字
  • 一位数 3[a]
  • 两位数 12[a]
  • 嵌套 2[3[a]]
  • 并列 2[a]3[b]

这个清单不完整，但比原来两眼一抹黑要强。

第二个是给调试代码加标记。

因为吃过亏了，我后来往代码里插调试语句都写成：

print(f"[DBG] cur={cur}")

提交前搜一下 [DBG]，比凭脑子记要好。临时改 return 的时候也在行尾写个 # TEMP。

第三个是别急着推倒重来。

第 3 次和第 4 次挂的时候，我第一反应都是「是不是算法想错了」，然后重新推一遍思路，浪费了很多时间。实际上只要回去看看自己刚才改了什么就行。

变量名的事

还有一个算是意外的发现。

我第 4 次挂是因为以为 stack[0] 存的是结果。后来我把变量名改长了：

  • cur 改成 current_segment
  • prev 改成 outer_prefix

名字长了打字麻烦，但我确实很少再搞混了。

最后

这篇写的时候我 2024 年，刚接触算法没多久，很多东西说不太明白，只能把过程记下来。

当时最大的感受是：「会做」和「能过」好像是两回事。 思路我是从题解学的，但照样挂了四次。

到底是哪里出了问题，那时候我也说不清。现在回头看，大概就是「没想过自己会在哪里错」。
